Reflection

One key design decision I made was to build the customer support agent around specialized tools rather than relying on the language model to answer everything directly. The agent uses AgentCore Gateway for hotel and booking APIs, a Knowledge Base for company and loyalty information, AgentCore Memory for multi-turn conversations, Code Interpreter for loyalty discount calculations, and Browser for web-based tasks. I chose this approach because each tool has a clear responsibility, while the agent acts as the orchestration layer that decides which tool to use. This also reduces the risk of the model inventing customer-specific information such as booking details, hotel prices, or loyalty benefits.

For a production environment, I would improve the agent through stronger security, observability, and reliability controls. I would apply least-privilege IAM policies, securely authenticate customers, add structured logging and tracing, and use CloudWatch alarms to detect elevated error rates. I would also add automated tests for individual tools, retries and graceful fallbacks for temporary service failures, input validation, and monitoring of tool latency and model usage. Finally, I would separate development and production environments and introduce a controlled CI/CD process so changes can be tested before reaching customers.

Challenge and Resolution:
One of the main challenges I encountered was integrating multiple AWS services with the deployed AgentCore Runtime. Although components such as the Knowledge Base and Browser worked independently in the AWS Console, they initially failed when invoked through the agent because the runtime execution role did not have the required IAM permissions. I diagnosed the issue by enabling error logging and reviewing the AgentCore Runtime logs in CloudWatch. The logs revealed specific AccessDeniedException errors, such as missing bedrock:Retrieve permission for the Knowledge Base and missing permissions required to start AgentCore Browser sessions. I resolved the issue by updating the runtime execution role with the required IAM policies and ensuring that the policies referenced the correct AWS resources. I then tested each tool again through the deployed agent to verify that the integrations worked successfully. This challenge taught me the importance of distinguishing between permissions available to my own AWS user and those available to the execution role used by a deployed application, as well as the value of CloudWatch logs for troubleshooting service integrations.
